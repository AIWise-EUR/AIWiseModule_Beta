## Compatibility contract

- Existing `schema:1` draft keys, submitted copies, IDs, author IDs, decisions,
  versions and releases are retained. No existing content rows are migrated.
- `slots._studio` is optional: `{version:1, formats:[], boxes:[]}`. All original
  `c2.block-N`, `extra-N` and course-slot labels stay unchanged. The extension is
  ignored only when absent; unknown or malformed extensions are rejected.
- Formats identify an existing slot and field path and contain allowlisted text
  runs. Their concatenated text must equal the plain field. Authored HTML is never
  parsed. Colors are six-digit hex; sizes are allowlisted.
- New Common boxes have UUIDs and identify a source block, a supported template and
  an anchor index within that unchanged source block. Their order is the saved array
  order within that placement. No raw selector, HTML, style string or script is saved.
- C2 course examples may contain 1–50 cards; optional context notes remain optional.
  Other existing array shapes stay fixed. Formatting follows examples on moves and
  duplication. Added boxes have their own UUIDs; old Common block IDs are not shifted.
- Only JavaScript cache-stamp changes are ignored when comparing a saved Common
  draft's source HTML. Actual markup changes remain protected. Changed approved
  baselines now open [visual draft recovery](studio-draft-recovery.md), preserving
  the original and requiring choices for overlapping changes before saving.
- A previously pending request remains an immutable old-format request. It can still
  be approved if its original baseline is current. Once another request for that
  scope/chapter/language is approved, the normal stale-approval guard requires revision;
  an older request cannot erase the newer boxes. This was already the approval policy.
- Existing approved/published snapshots are not regenerated by this update. Prepare a
  fresh release after activation; older already-frozen release candidates still carry
  their original JavaScript and should not be used to publish new-format content.

## User flow and scope

In English Common Studio, edit the existing group, choose **Add same box after…**,
select the existing box (for the requested C2 addition: Motor and bodily features,
third gradient row), then edit the added box's title/body in that panel. **Add text
box** places a plain title/body box after the selected group. New boxes can be
reordered within the same placement, duplicated, removed, aligned and resized.
Original Common containers cannot be deleted or rearranged in this first version:
that would change existing source IDs and review anchors.

Content Studio supports additional C2 example cards and text boxes after a content
slot. Existing cards use the actual module carousel renderer, including counts/dots.
Rich text controls appear below editable text fields. Select words in the input;
formatting is shown both below it and in the real module preview. Plain text inputs
prevent pasted HTML. Undo/redo history is in-session; Save draft persists the result.

All new authoring controls are English-only. Attribute values, page titles and SVG
labels stay plain. Existing Dutch workflows keep their previous behavior.

The real `workspace_studio_capabilities` RPC gates the controls. If the backend is
not updated, old text editing remains available. Authentication, role checks,
submission ownership and approval/publishing steps are not bypassed.

## Implementation map

- `pipelines/common-content.js`: allowlisted extension model, source-compatible Common
  renderer, safe text runs, copied components. Embedded here so the existing frozen
  release file set carries the implementation without extra public files.
- `workspace/studio-editing.js` and CSS: existing editor panel integration, formatting,
  added-box controls, C2 array controls, undo/redo and backend capability check.
- `workspace/content-studio.js`, `common-studio.js`: save/restore/preview and catalogs.
- `workspace/control-tower.js`: validates frozen copies, shows text/box comparisons.
- `pipelines/beta-content.js`, `published-content.js`, `course-loader.js`: approved
  extensions travel with course content and render after the existing slot renderers.
- SQL setup: pure validators plus a capability RPC. No UPDATE/DELETE/INSERT against
  existing content or request tables; no changes to submit/decision roles or checks.
- Both Edge Functions validate and carry the extension. Each entry point contains
  its validator so the owner's Dashboard deployment needs no additional dependency.
